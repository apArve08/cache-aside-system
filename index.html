How it works

The Node app is the only coordinator. Redis and Postgres never talk to each other, so every consistency guarantee comes from the order the app touches them.

Clientbrowser · k6
→
Node app :3000Express · cache-aside middleware
→
Redis :6379fast tier · TTL 300 s
PostgreSQL :5432source of truth · 20,000 rows

Read path · GET /logs?page=N

  1. Build key logs:page:N and GET it from Redis.
  2. Hit: return the cached JSON. Postgres is never touched.
  3. Miss: take a SET NX lock so only one request rebuilds the entry.
  4. Lock holder queries Postgres and writes the result with a TTL; waiters poll and read it.

Write path · PATCH /logs/:id

  1. BEGIN, UPDATE the row, COMMIT.
  2. After commit, DEL log:id so the next read sees the new value.
  3. Delete again 500 ms later to clear any stale value a racing read re-cached.
  4. The TTL is the backstop for a crash between commit and delete.

How I develop

The same loop for every layer: draw it, build the smallest piece, prove it by hand, then lock the proof into something repeatable before moving on. The commands and snippets below are the ones I used, trimmed for space.

Build one layer at a time

Docker for Redis and Postgres, a seed script for 20,000 rows, then a connection check, before any business logic sits on top. If something breaks later, it is the logic, not the infrastructure.

docker-compose.yml

Prove each layer by hand

Two curl calls and a redis-cli TTL show MISS then HIT. A PATCH followed by a read shows the old value is gone. Only then do I stack the next layer on top.

Terminal

curl -si localhost:3000/logs/42 | grep -i x-cache      # MISS
curl -si localhost:3000/logs/42 | grep -i x-cache      # HIT
redis-cli TTL log:42                                   # counting down from 300

curl -s -X PATCH localhost:3000/logs/42 \
  -H "Content-Type: application/json" -d '{"status":"done"}'
sleep 1                                                # let the delayed DEL finish
curl -si localhost:3000/logs/42 | grep -iE "x-cache|status"   # MISS, status done
Gate X-Cache goes MISS → HIT, and a PATCH forces a fresh read

Make the proof repeatable, then try to break it

Hand checks become a node:test suite. Then I remove the cache eviction on purpose. A test that has never failed might be asserting nothing, so two of three failing is what makes the passing run evidence.

test/cache.test.js (excerpt)

test('2. no stale cache after concurrent reads during writes', async () => {
  for (let i = 2; i < 22; i++) {
    const status = `v${i}`;
    // one write and 20 reads at the same moment
    await Promise.all([patch(id, status), ...Array.from({ length: 20 }, () => get(id))]);
    await sleep(700);                                  // let the delayed DEL finish
    const cached = await redis.get(`log:${id}`);
    if (cached) assert.equal(JSON.parse(cached).status, status, `stale cache at iteration ${i}`);
  }
});

Keep a control group

One CACHE_ENABLED switch runs identical code with Redis bypassed, so the only difference between runs is the cache. Without it, an improvement could be anything.

if (process.env.CACHE_ENABLED === 'false') {

Measure with a fixed protocol

Flush Redis and reset its counters before every run. Start the CPU sampler and k6 from one script so they cannot drift apart. Run three pairs and report the median, because a single run can mislead.

Terminal · one run (repeat for OFF and ON, three pairs)

R=$(docker ps -qf name=redis)
docker exec $R redis-cli FLUSHALL
docker exec $R redis-cli CONFIG RESETSTAT              # hit rate now covers this run only

# sampler and k6 start together: sum CPU of every postgres process, once a second (macOS)
top -l 62 -s 1 -stats command,cpu \
  | awk '/^Processes:/ {if (n) print s; s=0; n++} /^postgres/ {s+=$2} END {print s}' \
  > pg-cpu-on-1.log &
ENDPOINT=list THINK=0 TARGET=200 k6 run --summary-export=on-list-1.json load-test.js
wait

docker exec $R redis-cli INFO stats | grep -E "keyspace_(hits|misses)"
awk 'NR>1 {s+=$1; n++} END {printf "avg postgres CPU: %.1f%%\n", s/n}' pg-cpu-on-1.log
Gate same steps every run, medians not single results

What I learned, and the limits

The careful reading of the numbers is part of the result.

Caching pays for expensive queries

Single-row primary-key lookups showed no clear gain. A sorted 50-row page did, because the cache had real work to replace.

Check the test measures the right thing

Early runs returned ~345-byte bodies: the old script was still hitting the single-record route. A body-size check now fails loudly.

One run is an anecdote

Identical cache-on runs ranged from 9.3k to 17.3k req/s. The median of three kept a bad run from deciding the conclusion.

Tests must be able to fail

Commenting out the eviction made two of three tests fail with clear messages, which is what makes the passing run evidence.

Limits

Stated so the results are not over-read.

  • k6, Node, Redis and Postgres shared one laptop, so client and server competed for CPU.
  • The 3,000-user pair is a single run. Its cache-on failures (0.89%) were client-side connection timeouts; the server logged no errors.
  • Postgres CPU is summed across cores, so it can exceed one core's worth.
  • Built in JavaScript with node-redis and a local Postgres, not the TypeScript / ioredis / Dockerised Postgres in the original spec.
  • A process crash between COMMIT and the cache delete is not tested; the TTL bounds the staleness.
